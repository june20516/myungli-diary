# 검수 피드백

앱을 검수하고 다듬는 단계에서 사용자가 스크린샷과 자연어로 던지는 피드백을, 단위 세션이 바로 일할 수 있는 작업으로 나눠 보내는 절차입니다. 설계는 [spec](../specs/2026-10-28-review-feedback-design.md), 항목 대장은 [`items.md`](items.md)입니다. 지휘 세션이 맡습니다.

## 용어
| 용어 | 뜻 |
| --- | --- |
| 원요청 | 사용자가 던진 말과 스크린샷, 그대로. 고치지 않고 남깁니다 |
| 피드백 항목 | 원요청을 "한 화면, 한 문제"로 쪼개고 다듬은 것. 번호 `F-<세 자리>`와 심각도를 붙입니다 |
| 작업 | 항목을 단위 하나가 처리할 크기로 바꾼 것. 단위 Issue 하나가 작업 하나입니다 |
| 검수 회차 | 사용자가 "지금부터 검수"로 몰아서 던진 한 묶음. 수시 원요청은 회차 없이 쌓입니다 |
| 심각도 | S1 막힘, S2 불편, S3 다듬기 |

## 흐름
1. **받기:** 원요청을 원문 그대로 비공개 내부 저장소 `review/inbox/`에 적고, 스크린샷은 `review/shots/<날짜>/`에 둡니다. 수시 원요청은 `<날짜>.md`, 검수 회차는 `<날짜>-회차<n>.md`입니다.
2. **쪼개기:** 원요청을 항목으로 나눠 `items.md`에 적습니다. 화면은 `docs/ia/screens.json`의 id이고, 화면 밖 문제(알림, 스토어 문구 등)는 가장 가까운 IA id나 `-`를 씁니다. 원요청 칸은 링크 없이 "비공개 기록 `review/inbox/<파일>` #<n>"으로 적습니다(D74).
3. **대조:** 열린 항목, 열린 Issue, 결정 로그와 비교합니다. 같은 화면의 같은 문제는 묻지 않고 기존 항목에 원요청만 더합니다. `끝남` 항목과 같은 문제가 다시 나오면 새 항목을 만들고 문제 칸에 앞 번호를 적습니다.
4. **확인:** 아래 넷만 묶어 사용자에게 묻습니다(선택지 2~3개와 "다 아님"). 묻는 동안 항목 상태는 `확인 중`이고, "다 아님"이면 `확인 중`으로 두고 설명을 더 듣습니다. 답이 제품 결정이면 결정 로그(D)에 적고 그 번호를 항목과 작업 Issue에 답니다.
   * 두 원요청이 반대 방향일 때
   * 이미 정한 결정(D, 단위 결정)과 부딪힐 때
   * 고치는 길이 둘 이상이고 제품 판단이 필요할 때
   * 뜻이 두 가지로 읽힐 때
5. **나눠 보내기:** 항목을 단위 작업 Issue로 열고, 채팅으로 "보낸 작업 요약"(항목 번호, 단위, Issue 번호, 심각도)을 보고합니다.
6. **추적, 닫기:** 항목의 작업 Issue가 모두 닫히면 정기 일과에서 `끝남`으로 바꿉니다.

## 단위 배정 (원인 기준)
| 원인 | 단위 |
| --- | --- |
| 문구, 말투, 용어 | writing |
| 모양, 배치, 간격, 색, 글자 수 상한 | design |
| 동작, 화면 이동, 상태 처리, 성능 | app |
| 응답 데이터, 콘텐츠 렌더, 알림 | server |
| 계산 결과(사주, 용신, 길흉) | core |
| 화면 구성, 슬롯, 흐름(IA) | 지휘가 IA를 고친 뒤 받는 단위로 |

* 원인이 둘이면 작업을 둘로 나누고, 계약을 주는 쪽(design, writing, server)을 app보다 먼저 둡니다.
* 원인을 모르면 app에 "원인 찾기" 작업으로 보내고, app이 원인을 코멘트하면 다시 배정합니다. 원인 찾기 작업은 그때 원인 찾기로 닫습니다.

## 작업 Issue
* 라벨: `from:root`, `to:<단위>`, `kind:request`, `review`, `accepted`, 그리고 심각도 라벨 **하나**(`sev:1`, `sev:2`, `sev:3` 중 항목의 심각도)
* 제목: `[review F-<n>] <화면> <문제 요지>`
* 본문(`docs/workflow.md` §5.2 형식):
  * **무엇이 필요한가:** 화면, 상태, 재현 방법(대역 모드 시나리오 등), 문제, 바라는 것
  * **왜:** 원요청 요지. 스크린샷은 비공개라 말로 옮기고, 개인 정보가 없는 대역 화면이면 공개 저장소의 스크린샷 경로(`*/docs/artifacts/`)를 적습니다
  * **순서:** 작업이 둘 이상이면 무엇이 먼저인지
  * **관련:** F 번호, 관련 결정
* 단위 PR은 `Closes #<작업>`으로 닫습니다.

## 처리 순서
* 단위의 할 일 순서: drift → `sev:1` → 로드맵 일 → `sev:2` → `sev:3`. `sev:2`와 `sev:3`은 지휘가 박자마다 로드맵 일과 섞어 고릅니다.
* 로드맵 "현재 진행 순서"의 단위 행에 열린 review 작업 수를 심각도별로 적습니다.
* 단위가 동의하지 않으면(단위 결정과 부딪힘, 더 나은 방법) 고치지 않고 작업 Issue에 이유를 코멘트합니다. 지휘가 사용자에게 다시 확인합니다.
