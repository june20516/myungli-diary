# 브랜드 기반과 정체성 문서 체계 — 설계

* 작성: 지휘 세션, 2026-10-10
* 상태: 사용자 검토 대기
* 관련 결정: D13, D16, D19, D20, D22, D27, D28, D36, D37, D38~D40
* 이 문서의 결과물: `docs/identity/README.md`(브랜드 기반 확정본), `docs/identity/writing/`·`docs/identity/design/` 작업 단위 착수 안내, 규약·로드맵·계약 개정

## 1. 목적

디자인과 UX 라이팅에서 AI slop을 걷어내고, 명리일기만의 목소리와 시각 정체성을 세웁니다. 앞으로 화면 문구와 콘텐츠 문장(W1, Phase 2 LLM 코멘트)은 대부분 AI가 초안을 씁니다. 그래서 **사람이든 AI든 같은 기준으로 만들고 검수할 수 있는 기준**이 필요합니다.

사용자가 정한 결과물 범위는 세 가지 모두입니다.
* (A) 기준 정의: 보이스·시각 원칙과 하지 않을 것
* (B) 검수 장치: slop 패턴을 잡아내는 검사기
* (C) 기존 문서 정비: 00~06의 예시 문구와 06 디자인 시스템을 새 기준으로 대체

## 2. 작업 분해

## 3. 컨셉과 포지셔닝

**컨셉 문장 (팀 내부용):**
> 오늘 일진을 내 사주에 맞춰 풀어주는 일기 앱

* 사용자에게 보이는 태그라인·스토어 문구는 라이팅 시스템에서 따로 정합니다.
* 사용 순서(아침 알림·밤 일기)로 경험을 제약하는 표현은 쓰지 않습니다.

**포지셔닝:** 강점은 사주 일반이 아니라 **내 사주로 조합한 개인화**입니다.
* 사주 앱과 비교하면: 데일리·일간·주간·월간 운세는 띠나 일간 단위라 같은 날 같은 결과를 받는 사람이 많습니다. 명리일기는 일진 × 원국(D13)으로 사람마다 다른 오늘을 줍니다.
* 일기 앱과 비교하면: 일기 앱은 매일 같은 빈 페이지를 냅니다. 명리일기에서는 날마다 다른 오늘(D19 날의 성격, D22 가이드 질문)이 그날 일기의 출발점이 됩니다.

## 4. 성격

| 이렇다 | 이렇지 않다 |
| --- | --- |
| **차분하다:** 강조는 배지·색이 맡고 문장은 담담합니다 | 들떠 있다: 느낌표, 이모지, "완전 좋은 날" |
| **구체적이다:** 무엇이, 언제, 어떻게인지 말합니다 | 목적 없이 추상적이다: 기능 안내에서 "흐름이 보여요" |
| **곁에 있다:** 위로·공감이 목적인 자리에서는 운세체의 다정함도 씁니다 | 아무 데서나 다정하다: 정보 슬롯에서 "마음의 온도" |
| **아는 만큼 보여준다:** 문장에는 용어만 두고, 표시로 알아보게 하고, 풀이는 한 단계 아래에 둡니다 | 가르치려 든다: 괄호 풀이, 처음부터 용어 설명 |
| **이름을 불러준다:** 한 화면에 한 번 호칭으로 부릅니다 | 친한 척한다: 문장마다 이름을 부름 |

존재 비유는 **"내 기록을 같이 보는 일기장"**입니다(라운드 1). 문장이 하는 일은 **행동 조언·상태 설명·감정 돌봄** 세 유형입니다(라운드 2). 기록 권유와 메모식 요약은 쓰지 않습니다.

## 5. 원칙

1. **원칙 0. slop은 표현 자체가 아니라 맥락과 빈도에서 생깁니다.**
   * 추상적이거나 운세체인 표현도, 슬롯의 목적이 위로·공감·감정이고 그런 상호작용 맥락이 있으면 허용합니다.
   * slop이 되는 경우: ① 목적·맥락이 없는 자리에서 쓸 때 ② 한 화면·하루·한 주 안에서 남발할 때.
2. **낮은 주의력으로도 알아볼 수 있어야 합니다.** 읽지 않고 훑어봐도 날의 성격과 용어 여부를 알 수 있게, 글보다 UI 표시(꾸밈·색·배지)를 먼저 씁니다.
3. **강조는 UI가, 문장은 담백하게.** 날의 성격과 강도는 배지·색으로 전합니다. 문장에서 느낌표·이모지로 들뜨게 만들지 않습니다.
4. **영어로 생각하고 한국어로 옮긴 문장을 쓰지 않습니다.** 컨셉 문장 초안 검수(부록 B)에서 나온 패턴을 라이팅 시스템의 slop 목록 첫 항목들로 삼습니다.

## 6. 공용 용어와 부품

* **깊이 (D37):** `surface` 표면 → `explain` 풀이 → `evidence` 근거. 사용자 설정은 "기본 깊이"입니다.
* **호칭 (D36):** 온보딩 필수 입력, 실명이 아니어도 됩니다. 한 화면에 한 번만 부릅니다. 한국어 "님"·일본어 "さん" 접미사, 조사 처리, 입력 검증은 라이팅 시스템이 정합니다.
* **용어 토큰:** 문장 안의 명리 용어를 꾸밈·색으로 표시하고, 탭하면 `explain` 단계를 엽니다.
  * 라이팅: 어떤 단어를 용어로 표시할지 정합니다.
  * 디자인: 표시 방식과 열리는 화면을 정합니다.
* **문장 유형:** 조언(`advice`) · 상태(`state`) · 돌봄(`care`). 콘텐츠 구조의 축입니다(D40).

## 7. 시각 방향

* **톤:** 파스텔 그라데이션 바탕(06의 세이지 그린 → 코랄 핑크 계열) + 둥근 고딕 본문(고운돋움, SIL OFL).
  * 그라데이션은 AI 화면에서 흔한 인상이라는 점을 알고 고른 **조건부 선택**입니다. 사용해 보고 불쾌감이 들면 리뉴얼합니다. 디자인 시스템은 그라데이션을 토큰 하나로 묶어 교체 비용을 낮춥니다.
* **정보 가시성:** C안(차분한 데이터)처럼 정보를 칩·표시로 정돈합니다. 예쁨과 가독성이 부딪히면 가독성을 우선합니다.
* **데일리 카드 레이아웃 (L1):** 흰 패널 없이 그라데이션 바탕 위에 날짜 → 날의 성격 배지 → 문장(용어 토큰 포함) → 아래쪽 반투명 칩 한 줄(행운 색 견본·방향·숫자).
* 시안 파일은 로컬 `.suberpowers/brainstorm/`에 있습니다(git 제외). 디자인 시스템이 V0에서 이 방향을 정식 시안으로 다시 그립니다.

**참고할 기존 접근법**
* Mailchimp Content Style Guide: 보이스(고정)와 톤(상황별) 분리
* NN/g 톤의 4차원: 유머↔진지, 격식↔캐주얼, 존중↔파격, 열정↔담백 (슬롯별 톤 좌표)
* Torrey Podmajersky, 『Strategic Writing for UX』: voice chart
* Kinneret Yifrah, 『Microcopy: The Complete Guide』: 유형별 마이크로카피 규칙
* Sarah Richards / GOV.UK 콘텐츠 디자인: 사용자 필요를 먼저 쓰기
* 토스 UX 라이팅 원칙(공개 자료): 인용 전 원문 확인

**친숙도 검수 절차**
* **사람 검수:** 지휘 세션이 n지선다를 내고 사용자가 택일하는 라운드를 반복합니다.
  * 선택지에는 항상 "다 별로"를 둡니다.
  * slop 대조군을 숨겨 섞고, 같은 문항을 순서를 바꿔 다시 냅니다(일관성 확인).
  * 일부 선택지는 실제 커뮤니티·리뷰 표현에서 가져오고, 출처는 고른 뒤 공개합니다.
  * 판정자는 사용자 한 명입니다. 같은 성격의 선택이 반복되면 규칙으로 굳힙니다.
* **한국어 레퍼런스:** 브런치, 블라인드, 다음카페, 네이트판, 더쿠, 인스티즈 같은 온건한 커뮤니티와 커머스 리뷰.
  * 대량 수집(크롤링)은 대부분 약관 위반이므로 하지 않습니다. 표현 단위 검색으로 실제 쓰임을 확인합니다.
  * 자동 빈도 비교에는 합법적으로 쓸 수 있는 말뭉치(국립국어원 모두의 말뭉치 등)를 씁니다.
* **영어·일본어:** 같은 기준으로 레퍼런스를 고르되, 원어민 검수(D28, W1)를 대신하지 않습니다.

## 10. 정체성 문서 체계와 규약 개정 (D38)

`docs/identity/`는 **"지금 유효한 정체성 기준"** 층입니다. 원본 입력(`docs/background/` 00·03·06)의 정체성 내용을 대체하고, 원본은 그대로 둡니다.

```
docs/identity/
  README.md          브랜드 기반 확정본 (지휘)
  writing/           라이팅 시스템 작업 단위 — 세션은 여기서 시작
    CLAUDE.md  decisions.md(W#)  specs/  plans/  tools/ …
  design/            디자인 시스템 작업 단위 — 세션은 여기서 시작
    CLAUDE.md  decisions.md(V#)  specs/  plans/  tokens/  components/ …
```

함께 고칠 문서:
* 루트 `CLAUDE.md`: 세션 판별에 `docs/identity/writing|design` 추가, 문서 위치 표에 `docs/identity/` 추가
* `docs/workflow.md`: 역할 표, 소유권 표(`docs/identity/README.md`는 지휘, `writing/`·`design/`은 각 작업 단위), 결정 로그 접두어(W#, V#), 요청함 이름 규칙(`writing`, `design` 추가). spec·plan 경로는 작업 단위 디렉터리 바로 아래 `specs/`, `plans/`입니다(이미 `docs/` 안이므로 `docs/`를 한 번 더 두지 않습니다).
* `docs/contracts/README.md`: "브랜드 기반" 계약 추가(지휘 → writing, design), "디자인 토큰" 원본 위치를 `docs/identity/design/tokens/`로 변경(제공 design, V1 동결)
* `docs/background/README.md`: 정체성 내용은 `docs/identity/`가 00·03·06을 대체한다는 안내
* `docs/roadmap.md`: §11
* `docs/identity/writing/CLAUDE.md`, `docs/identity/design/CLAUDE.md`: 범위, 소유 경로, 제공·사용 계약, 현재 상태, 다음 할 일

## 12. 이 spec에서 함께 정한 결정

* **D38:** 정체성 문서 체계 `docs/identity/`와 writing·design 작업 단위 (§10)
* **D39:** MVP 화면 목록(IA)은 지휘 세션이 만들어 계약으로 고정합니다. app, writing, design 셋이 모두 기대고 app은 아직 시작 전이기 때문입니다. app은 이 목록을 받아 화면 흐름과 상태 관리를 설계합니다.
* **D40:** 콘텐츠는 문장 유형(조언·상태·돌봄) 축으로 만들고, MVP에서는 유형을 순환해 보여주며 사용자 반응(좋아요)을 **수집만** 합니다. 반응에 맞춰 유형을 고르는 적응형 선택은 Phase 2입니다.
  * 반응은 같은 날 종류(D19) 안에서 유형끼리 비교해야 의미가 있습니다. 내용(좋은 날)에 대한 반응과 섞이기 때문입니다.
  * 영향: server(반응 저장, 유형 순환), app(반응 UI), W1 분량 약 3배.

## 부록 B. slop 패턴 (라이팅 시스템의 출발점)

1. **목적 없는 자리의 과한 추상화.** 기능·정보 슬롯에서 무엇이 어디서 어떻게인지 말하지 않는 문장("흐름이 보여요", "나를 알게 돼요"). 실제 결과를 구체적으로 씁니다. 위로·공감 슬롯은 원칙 0에 따라 예외입니다.
2. **"X는 ~한 Y입니다" 정의형 소개.** 영어 "X is a Y that…"의 틀. 무엇을 해주는지부터 말합니다.
3. **사물 주어 의인화.** "사주를 아는 일기장"처럼 영어식 관계절로 사물이 알고 느끼게 하는 문장.
4. **시점 혼재와 기획 용어 노출.** 한 문장에서 "내"와 "사용자"가 섞이거나, 기획 용어("사용자", "콘텐츠")가 사용자 문장에 나옴.
5. **번역 슬로건 클리셰.** "주인공은 언제나 당신" 같은 틀.
6. **자기 성격 형용.** "차분하게 알려드려요"처럼 톤 규칙을 문장에 꺼내 놓음. 성격은 문장으로 드러냅니다.
7. **내용 없는 균형 병렬.** 대칭을 맞추느라 내용이 비는 구조. "A도 B도 아닌 C"가 대표적입니다.
8. **들뜬 강조.** 느낌표·이모지로 날의 성격을 강조함(원칙 3).
