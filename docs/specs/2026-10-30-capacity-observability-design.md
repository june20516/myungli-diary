# 관측(O1)과 부하 테스트, 용량 산정(L1): 준비 메모

* 작성: 지휘 세션, 2026-10-30
* 상태: 초안(준비 메모). 착수 때 사용자와 범위를 확정하고 승인받습니다
* 착수 시점: O1은 T1 전(테스터가 쓰기 시작할 때 크래시와 장애가 바로 보여야 하므로). L1은 T1과 나란히

## 1. 목적

* **O1 관측:** 앱 크래시, server 오류, 인프라 장애를 사람이 찾아보기 전에 알 수 있게 합니다.
* **L1 부하와 용량:** 요청 하나에 드는 연산과 비용, 버틸 수 있는 동시 사용자 수를 숫자로 잡습니다. 비슷한 범주 앱의 활성 사용자 규모(대형, 중형, 소형)를 기준으로, 지금 설정이 버티는지와 못 버틸 때 무슨 일이 생기는지, app이 그 상황에 대응하는지 확인합니다.

## 2. 지금 상태(2026-10-30 저장소 확인)

| 항목 | 상태 |
| --- | --- |
| app 크래시 추적 | Firebase Crashlytics adapter 있음(`app/lib/core/platform/firebase_crash_reporter.dart`), debug에서는 수집 끔. staging release 빌드에서 실제로 보고가 들어오는지는 확인 전 |
| server 오류와 장애 알림 | Terraform에 monitoring, 알림 정책, uptime check, 예산 알림 리소스 없음 |
| Cloud Run 용량 설정 | server, 엔진 모두 인스턴스 수, CPU, 메모리, 동시 요청 수를 명시하지 않음(기본값이 적용, 값은 착수 때 확인). 엔진은 내부 전용, 호출은 server 서비스 계정만 |
| Cloud SQL | staging `db-f1-micro`, prod `db-custom-1-3840`. 연결 수 상한과 server 연결 풀 크기 대조 전 |
| server 과부하 보호 | rate limit, 부하 차단을 코드에서 찾지 못함(확인 필요) |
| app 과부하 대응 | 오류 화면 컴포넌트 있음. 429, 503, 시간 초과에서 재시도와 안내가 어떻게 되는지 확인 전 |
| 외부 health 확인 | `/healthz`는 직접 주소와 공개 주소 모두 Google 앞단의 404(Cloud Run 예약 경로로 보임, 확인 필요). `/v1/me`는 server의 401 응답이 와서 서비스는 정상. 외부 uptime check를 둘 경로는 착수 때 정함 |

## 3. O1 범위(T1 전)

1. Crashlytics: staging release 빌드에서 일부러 낸 오류가 콘솔에 들어오는지, 심볼(dSYM, Android 난독화 매핑) 업로드가 배포 workflow에 있는지.
2. server: Cloud Run 5xx 비율, 지연 시간, 인스턴스 수 상한 도달, Cloud SQL CPU와 연결 수, Job 실패에 알림 정책. 받는 곳은 사용자 메일(E14 주소와 별개로 정함).
3. 외부 uptime check(공개 주소 기준)와 예산 알림(두 프로젝트).
4. 알림이 오면 무엇을 보는지 한 장짜리 대응 절차(`server/` 또는 루트 문서, 착수 때 정함).
5. 알림 리소스는 Terraform으로 관리합니다(server 몫).

## 4. L1 범위(T1과 나란히)

1. **기준 규모:** 비슷한 범주 앱(사주, 운세, 일기)의 대형, 중형, 소형 활성 사용자 수를 조사해 시나리오 세 개로 만듭니다. 조사 원문과 수치는 비공개 저장소 `business/`에 둡니다(D74). 공개 쪽에는 "시나리오 S, M, L" 이름과 초당 요청 목표만 적습니다.
2. **사용 모델:** 하루 사용 흐름(아침 알림 뒤 데일리 열기, 일기 쓰기, 캘린더)을 요청 순서로 바꾸고, 아침 알림 직후 몰림을 최고점으로 잡습니다.
3. **측정:** 요청 종류별 지연 시간, 인스턴스당 처리량, 엔진 호출 비용(캐시 적중과 미적중), DB 부하, 사용자 수에 따른 월 비용.
4. **한계 확인:** 인스턴스 수 상한, DB 연결 상한, 엔진 상한에 닿았을 때 server가 무엇을 돌려주는지, app이 그때 어떻게 보이는지(재시도 폭주가 없는지).
5. **환경:** T1 테스터가 쓰는 staging을 흔들지 않도록, 같은 Terraform으로 띄우고 끝나면 지우는 부하 전용 환경을 우선 검토합니다. 안 되면 staging에서 테스터가 적은 시간에 짧게 돌립니다.
6. **결과:** 시나리오별로 버티는지, 못 버티면 어디가 먼저 막히는지, 고칠 것(설정값, rate limit, app 재시도 정책)을 server와 app에 요청합니다. 확정한 용량 설정은 결정 행으로 남깁니다.

## 5. 끝난 조건

* O1: 일부러 낸 앱 크래시와 server 오류가 알림으로 도착합니다. T1 시작 조건입니다.
* L1: 시나리오 세 개마다 결과(버팀, 막히는 곳, 비용)가 있고, 고칠 것의 Issue가 열려 있습니다. 출시(I4) 전까지 고칩니다.
