# 검수 피드백 워크플로 — 설계

* 작성: 지휘 세션, 2026-10-28
* 상태: 검토 중
* 관련: `docs/workflow.md` §5.2(요청함), §5.3(외부 준비물 대장, 같은 모양), D74(공개 저장소), D87(사용자 영향 표시)

## 1. 목적

앱 전체를 검수하고 다듬는 단계에서, 사용자가 화면 스크린샷과 자연어로 던지는 불만과 피드백을 **각 단위 세션(app, design, writing, server, core)이 바로 일할 수 있는 작업 목표와 단위**로 나눠 보냅니다.

* 사용자는 생각나는 대로 던지기만 합니다. 확인 질문은 꼭 필요한 것만 받습니다.
* 단위 세션은 작업 Issue 하나만 읽고 무엇을, 왜 고칠지 압니다.
* 어느 작업이 어느 불만에서 나왔는지 끝까지 거슬러 올라갈 수 있습니다.

## 2. 용어

| 용어 | 뜻 |
| --- | --- |
| 원요청 | 사용자가 던진 말과 스크린샷, 그대로. 고치지 않고 남깁니다 |
| 피드백 항목 | 원요청을 "한 화면, 한 문제"로 쪼개고 다듬은 것. 번호 `F-<세 자리>`와 심각도를 붙입니다 |
| 작업 | 피드백 항목을 단위 하나가 처리할 크기로 바꾼 것. 단위 Issue 하나가 작업 하나입니다. 항목 하나가 작업 여럿이 되거나, 항목 여럿이 작업 하나로 모일 수 있습니다 |
| 검수 회차 | 사용자가 "지금부터 검수"로 시작해 몰아서 던진 한 묶음. 수시로 던진 원요청은 회차 없이 쌓입니다 |
| 심각도 | S1 막힘(기능이 안 되거나 틀린 정보), S2 불편(쓰기 어렵거나 헷갈림), S3 다듬기(보기, 말투, 세부) |

## 3. 흐름

```
받기 → 쪼개기 → 대조 → 걸리는 것만 확인 → 작업으로 나눠 보내기 → 추적, 닫기
```

입력은 두 리듬을 모두 받습니다. 수시로 던진 원요청과 검수 회차의 원요청이 같은 항목 대장에 쌓입니다.

1. **받기.** 지휘가 원요청을 원문 그대로 비공개 내부 저장소에 적고 스크린샷을 저장합니다(§4).
2. **쪼개기.** 원요청 하나를 피드백 항목으로 나눕니다. 항목마다 번호, 화면 IA id(스크린샷을 `docs/ia/screens.json`의 화면과 맞춤), 문제(관찰), 바라는 것(사용자가 말한 방향, 없으면 비움), 심각도, 원요청 위치를 적습니다.
3. **대조.** 새 항목을 열린 항목, 열린 Issue, 결정 로그와 비교합니다(§5).
4. **확인.** 확인 대상만 묶어 사용자에게 묻습니다(§5). 나머지는 묻지 않고 진행합니다.
5. **나눠 보내기.** 항목을 단위 작업 Issue로 엽니다(§6). 보낸 뒤 채팅으로 "보낸 작업 요약"(항목 번호, 단위, Issue 번호, 심각도)을 보고합니다.
6. **추적, 닫기.** 작업 Issue가 모두 닫히면 지휘가 항목을 "끝남"으로 바꿉니다. 고친 화면은 다음 검수 때 사용자가 다시 보고, 남은 문제는 새 원요청으로 들어옵니다.

## 4. 저장 위치

스크린샷에는 T1 무렵부터 사용자 실제 계정의 생년월일, 사주, 일기 본문이 찍힐 수 있습니다. 공개 저장소(D74)에 두지 않습니다.

| 위치 | 담는 것 | 공개 |
| --- | --- | --- |
| 내부 저장소 `myungli-diary-internal/review/inbox/` | 원요청 원문. 수시 원요청은 `<날짜>.md`, 검수 회차는 `<날짜>-회차<n>.md`. 파일 안에서 원요청마다 `## #<n>` 머리를 두고 원문과 스크린샷 경로를 적습니다 | 비공개 |
| 내부 저장소 `review/shots/<날짜>/` | 스크린샷 원본 | 비공개 |
| 공개 저장소 `docs/review/items.md` | 피드백 항목 대장 | 공개 |
| 공개 저장소 `docs/review/README.md` | 이 절차 요약. `docs/workflow.md` §5.4가 여기로 이어 줍니다 | 공개 |

* 원요청은 D74 규칙대로 링크하지 않고 "비공개 기록 `review/inbox/<파일>` #<n>"으로만 적습니다.
* 공개 항목과 작업 Issue에는 개인 정보(생년월일, 사주 값, 일기 본문, 실명)를 옮기지 않습니다. 재현은 대역 모드 시나리오로 적습니다.

### 4.1. 항목 대장 `items.md`

| 번호 | 화면 | 문제 | 바라는 것 | 심각도 | 상태 | 원요청 | 작업 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F-012 | `today` | 총운 문장이 세 줄을 넘으면 카드가 잘림 | 잘리지 않게 | S2 | 보냄 | 비공개 기록 `review/inbox/2026-11-02.md` #3 | #701, #702 |

* **상태 값:** `받음` → `확인 중` → `보냄` → `끝남`. 그 밖에 `보류`(이유를 문제 칸 끝에 적음), `합침`(작업 칸에 합친 항목 번호 `→ F-<n>`), `버림`(사용자가 철회).
* 화면 칸은 IA id이고, 화면 밖 문제(알림, 스토어 문구 등)는 `system-push`처럼 가장 가까운 IA id나 `-`를 씁니다.
* 표는 번호 순서로 쌓고 행을 지우지 않습니다.

## 5. 대조와 확인

### 5.1. 대조 규칙

* **중복:** 같은 화면, 같은 문제면 기존 항목의 원요청 칸에 새 위치를 더하고 새 항목을 만들지 않습니다. 묻지 않습니다.
* **고친 뒤 다시 나온 문제:** 기존 항목이 `끝남`이면 새 항목을 만들고 문제 칸에 앞 항목 번호를 적습니다.
* **확인 대상:**
  1. 두 원요청이 반대 방향일 때
  2. 이미 정한 결정(D, 단위 결정 C·S·A·W·V)과 부딪힐 때
  3. 고치는 길이 둘 이상이고 제품 판단이 필요할 때
  4. 뜻이 두 가지로 읽힐 때
* 확인 대상 항목의 상태는 `확인 중`입니다.

### 5.2. 확인 방식

* 확인 대상을 묶어 한 번에 묻습니다. 문항마다 선택지 2~3개와 "다 아님"을 둡니다.
* 답이 제품 결정이면 결정 로그(D)에 적고, 그 번호를 항목과 작업 Issue에 답니다.
* 사용자가 "다 아님"을 고르면 그 항목은 `확인 중`으로 두고 설명을 더 듣습니다.

## 6. 작업으로 나눠 보내기

### 6.1. 단위 배정 (원인 기준)

| 원인 | 단위 |
| --- | --- |
| 문구, 말투, 용어 | writing |
| 모양, 배치, 간격, 색, 글자 수 상한 | design |
| 동작, 화면 이동, 상태 처리, 성능 | app |
| 응답 데이터, 콘텐츠 렌더, 알림 | server |
| 계산 결과(사주, 용신, 길흉) | core |
| 화면 구성, 슬롯, 흐름(IA) | 지휘가 IA를 고친 뒤 받는 단위로 |

* 원인이 둘이면 작업을 둘로 나누고, 계약을 주는 쪽을 먼저 둡니다(design·writing·server → app). 각 작업 본문에 순서를 적습니다.
* 원인을 모르면 app에 "원인 찾기" 작업으로 보냅니다. app이 원인을 코멘트로 적으면 지휘가 다시 배정하고, 그 작업은 원인 찾기로 닫습니다.

### 6.2. 작업 Issue

* 라벨: `from:root`, `to:<단위>`, `kind:request`, `review`, 심각도 `sev:1`·`sev:2`·`sev:3`, 지휘 수락 `accepted`
* 제목: `[review F-<n>] <화면> <문제 요지>`
* 본문(`docs/workflow.md` §5.2의 요청함 형식):
  * **무엇이 필요한가:** 화면, 상태, 재현 방법(대역 모드 시나리오 등), 문제, 바라는 것
  * **왜:** 원요청 요지. 스크린샷은 비공개라 말로 옮깁니다. 개인 정보가 없는 대역 화면이면 공개 저장소의 스크린샷 경로(`*/docs/artifacts/`)를 적습니다
  * **순서:** 작업이 둘 이상이면 무엇이 먼저인지
  * **관련:** F 번호, 관련 결정
* 단위 PR은 `Closes #<작업>`으로 닫습니다. 항목의 작업이 모두 닫히면 지휘가 정기 일과에서 항목을 `끝남`으로 바꿉니다.

### 6.3. 처리 순서

* 단위의 할 일 순서: **drift → `sev:1` → 로드맵 일 → `sev:2` → `sev:3`.** `sev:2`와 `sev:3`은 지휘가 박자마다 로드맵 일과 섞어 고릅니다.
* 로드맵 "현재 진행 순서"의 단위 행에 열린 review 작업 수를 심각도별로 적습니다.
* **단위가 동의하지 않을 때:** 단위 결정과 부딪히거나 더 나은 방법이 있으면 고치지 않고 작업 Issue에 이유를 코멘트합니다. 지휘가 §5.2로 사용자에게 다시 확인합니다.

## 7. 자동 검증

루트 docs 검사(`tools/docs-check`)에 `docs/review/items.md` 검사를 더합니다.

* 표 머리가 §4.1의 여덟 칸인지
* 번호가 `F-<세 자리>` 형식이고 겹치지 않는지
* 상태가 §4.1의 일곱 값 중 하나인지
* 심각도가 `S1`·`S2`·`S3` 중 하나인지
* `보냄`·`끝남` 항목의 작업 칸에 Issue 번호가 하나 이상 있는지
* `합침` 항목의 작업 칸이 존재하는 항목 번호를 가리키는지

원요청 파일은 비공개 저장소라 검사하지 않습니다.

## 9. 범위 밖

* 단위가 실제로 고치는 일(각 작업 Issue의 처리)
* 검수 회차를 언제 열지와 검수 체크리스트(화면 순서 등)는 첫 회차 때 사용자와 정합니다
* 테스터(T1) 피드백 수집 경로는 T1 운영 계획에서 정합니다. 들어온 테스터 피드백도 원요청으로 받으면 같은 흐름을 탑니다
