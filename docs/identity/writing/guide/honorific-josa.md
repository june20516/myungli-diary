# 호칭·조사 처리 규칙 (v1)

server(Go) 콘텐츠 렌더러가 원고 문장을 화면 문장으로 바꿀 때 따르는 계약입니다.

* 버전: v1
* 규칙 원본은 `rules/josa.yaml`, 판정표는 `generated/josa-table.md`입니다. 이 문서는 값을 옮겨 적지 않고 순서와 계약만 설명합니다.
* 테스트 자료: `rules/josa.yaml`의 `examples`(표기된 원고 → 렌더 결과)와 `name_rules.examples`(호칭 입력 → 저장값·코드). server 테스트가 그대로 읽어 씁니다.
* 결정 근거: `decisions.md`의 W5(호칭), W9(용어 토큰 표기), spec §7
* 기준 구현: `tools/src/mlw/josa.py`, `tools/src/mlw/placeholders.py`. 판정이 다르면 기준 구현과 `examples`를 따릅니다.

## 원고 표기

원고(`content/<lang>/*.yaml`)의 `text`에는 다음 표기만 씁니다.

| 표기 | 뜻 |
| --- | --- |
| `{param}` | 매개변수 값 자리. 값은 호출자가 줍니다. |
| `{param:category}` | 값 이름 사전(`glossary.value_name`)의 범주를 지정한 자리. 예: `{element:color}`는 오행을 색 이름으로 씁니다. |
| `(이)가` `(은)는` `(을)를` `(과)와` `(으)로` `(이)에요` | 조사 표기. 자리표시자나 값 바로 뒤에 붙입니다. 쌍은 `rules/josa.yaml`의 `pairs`가 전부입니다. |
| `[[용어]]` | 용어 토큰(W9). 명리 용어를 app이 토큰으로 보여 주도록 표시합니다. |

* 조사 표기는 `{color}(이)가`처럼 자리표시자 뒤에 오거나, 토큰의 닫는 `]]` 뒤에 올 수 있습니다.
* 문법이 틀린 원고(`{`와 `}` 짝 불일치, `[[`와 `]]` 짝 불일치·중첩·빈 토큰)는 검사 단계에서 막힙니다. server는 만나면 오류로 처리합니다.
* 메시지 키별로 쓸 수 있는 매개변수와 값 종류는 슬롯 명세(`slots/content/*.yaml`)의 `params` 맵이 정합니다. 아래 "값 종류별 렌더"를 봅니다.

## 값 종류별 렌더

슬롯 명세 `keys`의 `params`는 `매개변수: 값 종류` 맵입니다. 렌더러는 값 종류에 따라 값을 문장에 넣습니다.

| 값 종류 | 표기 예 | 렌더 |
| --- | --- | --- |
| 범주 목록 | `element: [element, color]` | `{element}`은 첫째 범주(기본 범주) 이름, `{element:color}`는 목록 안의 다른 범주 이름으로 바꿉니다. 목록에 없는 범주는 쓸 수 없습니다. |
| `list:<범주>` | `branches: list:branch` | 목록 값의 원소마다 그 범주 이름으로 바꾸고 쉼표와 공백(`, `)으로 잇습니다. 범주를 붙일 수 없습니다. |
| `number` | `score: number` | 숫자를 그대로 씁니다. 범주를 붙일 수 없습니다. |
| `none` | `role: none` | 문장에 쓸 수 없습니다. 원고에 나오면 검사기가 막습니다(`complete.unrenderable_param`). |

* 범주 이름은 `glossary.value_name`의 `<범주>.<값>` 원고입니다. 값은 엔진 enum 이름을 소문자로 바꾸고 접두어를 뗀 것입니다(예 `WOOD` → `element.wood`).
* 기본 범주가 아닌 범주로 렌더할 때 값의 대응은 다음과 같습니다.
  * `color`: `element`와 같은 값 집합입니다. `WOOD`는 `color.wood`입니다.
  * `ten_god_group`: 십성 값이 속한 그룹입니다(엔진 `TenGod.group`, 예 비견·겁재 → `bigyeop`).
* `name`(호칭)은 모든 슬롯에서 쓸 수 있고 `params`에 적지 않습니다. 범주를 붙일 수 없습니다.
* 검사기는 원고의 `{p}`·`{p:cat}`가 그 키의 `params`에 있는지(`complete.unknown_param`), 범주가 허용되는지(`complete.bad_category`), `none`을 쓰지 않았는지(`complete.unrenderable_param`) 봅니다.
* 글자 수 검사는 기본 범주(또는 고른 범주)의 가장 긴 이름, `list`는 가장 긴 이름 2개(집중 시간 엔진 상한)를 이은 값으로 셉니다. `number`는 값 범위를 몰라 건너뜁니다.

## 호칭 표기

호칭 접미사는 원고에 직접 적습니다(W5). 렌더러는 접미사를 붙이지 않습니다.

* 한국어: `{name}님`
* 일본어: `{name}さん`
* 영어: `{name}`
* `{name}` 값은 저장된 호칭(끝의 "님"을 뗀 값)입니다. 한국어는 항상 `님`이 뒤따르므로 조사는 받침 있음 형태로 고정됩니다.
* 접미사 선택 기능은 없습니다.
* 접미사가 빠진 원고는 검사기가 오류로 막습니다(`style.S4` 한국어, `style.S5` 일본어). 이 두 규칙은 NFC만 적용한 원문에서 판정합니다. server는 이미 검사를 통과한 원고를 받는다고 가정해도 됩니다.

## 렌더 순서

순서를 바꾸면 결과가 달라집니다. 반드시 이 순서를 지킵니다. 기준 구현은 `placeholders.substitute`입니다.

1. **NFC 정규화.** 원고와 입력 호칭을 유니코드 NFC로 바꿉니다. 호칭 입력은 NFD일 수 있으므로(예: macOS 입력) 길이 검사와 접미사 판정보다 먼저 합니다. 한글 음절 받침 계산도 NFC를 전제로 하므로 server도 같은 NFC 정규화를 먼저 합니다.
2. **토큰 구간 기억, 대괄호 제거.** `[[`와 `]]` 사이의 범위를 기억하고 대괄호를 지웁니다.
3. **값 치환.** `{param}`과 `{param:category}`를 위 "값 종류별 렌더" 규칙으로 바꿉니다. 이름이 없는 enum 값은 오류입니다. `{name}`은 저장된 호칭으로 바꿉니다. 저장된 호칭에는 `{ } [ ] ( )`가 없으므로(입력 검증) 치환한 값이 자리표시자·토큰·조사 표기로 다시 해석될 일이 없습니다. 접미사(`님`, `さん`)는 원고에 이미 있으므로 렌더러가 붙이지 않습니다.
4. **조사 렌더.** 조사 표기를 바로 앞 글자의 받침으로 골라 바꿉니다. 대괄호를 이미 지웠으므로 토큰 바로 뒤의 조사는 토큰 안쪽 마지막 글자가 기준입니다. 호칭 뒤라면 원고의 `님`(받침 있음)이 기준입니다.
5. **토큰 표시.** 조사가 바뀌면 글자 위치가 달라지므로, 2번에서 기억한 토큰 구간을 4번 뒤의 최종 문장 기준으로 다시 계산해 app이 토큰으로 보여 줄 수 있는 응답 형식으로 넘깁니다. 형식은 server 설계가 정합니다. 대괄호를 그대로 app에 넘기지 않는 것만 계약입니다.

## 조사 판정

* 판정표는 `generated/josa-table.md`입니다. 쌍별 받침 있음·없음 값, ㄹ 받침 예외(`(으)로`), 병기형은 `rules/josa.yaml`의 `pairs`에 있습니다.
* 앞 글자가 한글 음절이면 받침을 직접 봅니다. 유니코드 산식으로 종성 인덱스를 구하고, 0은 받침 없음, 8은 ㄹ 받침입니다.
* 숫자·영문·한자로 끝나면 `readings`로 읽는 소리를 구해 그 마지막 음절의 받침을 봅니다. 숫자 읽기는 아래 규칙을 따릅니다. 대상은 ASCII 숫자(0~9)와 ASCII 영문(A~Z, 대소문자 무관)입니다. 전각 숫자 등은 판정할 수 없는 글자입니다.
  * 끝의 숫자 덩어리를 한 수로 봅니다.
  * 수가 전부 0이면(0, 00) 끝자리 읽기 "영"을 씁니다.
  * 끝자리가 0이 아니면 그 자리의 읽기(`digits`)를 씁니다.
  * 끝에 0이 이어지면 연속한 0의 개수로 자릿수 읽기(1개 십, 2개 백, 3개 천, 4개 만)를 고르고, 개수가 최대치(4)를 넘으면 상한 "만"으로 자릅니다.
  * 경계값은 `examples`의 `0`, `100`, `1000`, `10000`, `100000` 항목이 보여 줍니다.
* 그 밖의 글자(기호 등)는 판정할 수 없습니다. 이때는 병기형을 씁니다.
  * `(이)가` → `이(가)`, `(은)는` → `은(는)`, `(을)를` → `을(를)`, `(과)와` → `과(와)`
  * `(으)로`와 `(이)에요`는 병기형이 어색하므로 표기 그대로 둡니다.
* **영문 판정 한계:** 여러 글자 영문 값은 마지막 글자의 알파벳 이름으로만 판정합니다. 예를 들어 `Bob`은 `B`의 "비"로 읽어 받침 없음이 되지만 실제 읽기 "밥"은 받침이 있습니다. 값 이름 사전이 한글 이름을 주므로 실제 문장에서는 드뭅니다.

## 호칭 입력 검증

저장 전에 아래 순서로 검증합니다. 값은 `rules/josa.yaml`의 `name_rules`에 있고, 기준 구현은 `normalize_name`입니다.

1. NFC 정규화 후 앞뒤 공백을 제거합니다.
2. 제어문자가 있으면 거부합니다(`name.control`).
3. 이모지가 있으면 거부합니다(`name.emoji`).
4. `forbidden_chars`의 글자(`{ } [ ] ( )`)가 있으면 거부합니다(`name.invalid_char`). 원고 표기(자리표시자, 용어 토큰, 조사 표기)와 섞이지 않게 하기 위해서입니다. 예: `민지(이)가`, `a]]`.
5. 언어의 `strip_suffix`(한국어 끝의 "님")를 반복해서 떼고 저장합니다(`name.suffix_stripped`, 거부가 아니라 알림).
6. 비면 거부합니다(`name.empty`).
7. 언어별 최대 길이를 넘으면 거부합니다(`name.too_long`). 길이는 NFC 정규화 뒤 유니코드 코드포인트 수입니다(기준 구현의 `len`). 자모 분리형 입력은 NFC로 합쳐진 뒤 셉니다.
8. 일본어 끝의 `さん`·`様`·`ちゃん`은 떼지 않고 경고만 합니다(`name.suffix_warning`).

거부하면 저장하지 않고 사유 코드를 돌려줍니다. 사용자에게 보여 줄 문구는 app 몫입니다.

## server 구현 확인 목록

* `examples`의 모든 항목이 렌더 결과와 같습니다.
* `name_rules.examples`의 모든 항목이 호칭 입력 검증 결과(저장값, 코드)와 같습니다.
* NFD로 입력한 `민지님`이 `민지`로 저장되고 `name.too_long`이 나지 않습니다.
* NFD로 쓴 `남색(이)가`가 `남색이`가 됩니다.
* 판정할 수 없는 글자 뒤의 병기형이 위 규칙과 같습니다.
* 렌더 결과에 `[[`, `]]`가 남지 않습니다.
