## 현재 진행 순서 (2026-11-17 기준, 유료 앱 계약 활성 뒤)
지휘 세션이 상태가 바뀔 때마다 고칩니다. 위 표의 선행 조건을 지금 상태에 대입한 결과입니다. 지난 순서는 [`roadmap-history.md`](roadmap-history.md)에 있습니다.

* **열린 `drift` Issue는 받는 단위의 다음 할 일 맨 앞에 둡니다**(D73, `docs/workflow.md` §6.1). 지금 열린 drift: 없음(2026-11-16).
* **동시에 도는 단위 세션은 둘까지입니다**(D78). 단위 PR은 사용자가 auto-merge를 걸어 두면 검사 통과 때 병합됩니다(D100 ②). CI는 `gh run watch` 없이 60초 이상 간격으로 확인합니다.
* **목표는 T1(비공개 테스트)입니다. 가장 긴 경로:** server 구매 내역 상품 식별자(#1264)와 app 최소 버전 확인(#1258) → T1 빌드 → 테스터 초대. Q1과 server → app 관문(D138)은 끝났습니다(2026-11-17).
* **실기기:** App Store 유료 앱 계약, 은행, 세금 양식이 활성되어 빌드 9에서 광고 제거권 sandbox 구매까지 확인했습니다(2026-11-17). 그때 나온 구매 경험 피드백: 구매 내역에 RevenueCat 내부 id가 보임(server #1264, T1 전), 결제 창이 늦게 뜸(app #1265, 구간 측정), 사용 중 상태와 자동 결제 없음 강조(design #1266, writing #1267, T1을 막지 않음).
* **환경 상태:** staging은 server(REST 1.13.1), 엔진(ruleset 2026.11.9), 결제, SSV, 미리 계산, 아침 알림, O1 알림, 문의 메일, 법적 문서와 지원 페이지까지 배포됐습니다. prod는 D135 최소 구성(최소 0대, `db-g1-small`)으로 떠서 스토어 URL(처리방침, 약관, 지원)을 내줍니다(2026-11-17). prod 승인은 prod에 의미 있는 server 변경만 받고 나머지는 지휘가 취소합니다. staging E2E는 `app/tool/patrol_staging.sh`이고 실행마다 `support@`로 `[E2E]` 메일이 옵니다.
* **I4 2주 전: Cloud SQL tier와 예산 점검(#903, D135 ④, 원래 2026-12-15).** 활성 추이와 L1 결과로 사용자가 정합니다: prod SQL을 `db-g1-small`에서 `db-custom-1-3840` 이상으로 올릴지와 시각(재시작 몇 분), prod 최소 1대 복귀(#817 ④), CPU 과금 방식. 금액은 비공개 L1 리포트(D74).
* **T1 전 남은 보안 일:** staging App Check debug token 교체(T1 직전, #1254). 스토어 콘솔 신고 수정(D137 ④), 로그 보관 90일, 결제와 보상 기록 축소는 끝남(S164, bootstrap apply, 2026-11-17).
* **server → app 관문(D138, D110 ⑦):** server CI가 이미 나간 앱 빌드를 깨는 계약 변경을 막습니다(S165, 2026-11-17). 꼭 깨야 할 때만 열린 enum 전환, 최소 지원 버전 올리기(staging과 prod 설정 둘 다), `/v2` 중 하나로 갑니다. app은 최소 버전 안내를 실기기로 확인합니다(#1258).
* **I4 전에 남은 일:** main과 staging 브랜치 분리(D136 ①, 설계는 지휘), Q1 뒤처리(server #1253, app #1254, core #1255), writing과 design workflow SHA 고정(#1236, #1237), SSV 주소 prod 전환, 스토어 출시 뒤 AdMob 앱 검토, LINE Published, 법적 문서 시행일.
