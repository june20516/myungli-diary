## 결론

* **한계점은 1회차와 같습니다.** warm은 초당 80세션(요청 694건/초)을 버티고 160에서 멈춥니다. cold는 이번에 `stage_80`에서 멈췄습니다(1회차 cold는 80을 버팀).
* **처음 막히는 곳은 여전히 Cloud SQL CPU이고, 원인은 query 횟수입니다.** warm `stage_80`에서 SQL에 query가 초당 4,117건(요청 하나당 약 6건) 들어가 1 vCPU가 100%에 닿았습니다. query 하나의 실행은 0.03~0.06ms로 짧고, 회차 전체 실행 시간 합도 1 vCPU의 몇 %입니다. 느린 query가 아니라 query마다 드는 고정 비용이 쌓여 CPU를 씁니다. 새 연결은 2분에 8~12개로 일정해 연결 비용은 원인이 아닙니다.
* **엔진 동시 요청 8의 효과는 아직 확인하지 못했습니다.** 두 회차 모두 429는 0건이지만, 1회차에서 엔진 429가 나던 cold `stage_160`까지 가지 못했습니다(SQL이 더 이른 단계에서 막힘).
* **CPU 할당량(load 20 vCPU)은 측정에 닿지 않았습니다.** 최대 인스턴스는 server 3, 엔진 3이고 생성기 8 vCPU를 더해도 약 14 vCPU입니다. 64 vCPU 증가 신청은 자동 거절됐지만(아래 "환경") 결과는 prod와 같은 용량으로 볼 수 있습니다.
