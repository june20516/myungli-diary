# L1 한계점 측정 3회차 (2026-11-09)

2회차는 [`../2026-11-09-limit-2/`](../2026-11-09-limit-2/README.md), 파일 형식은 [`load/README.md`](../../../load/README.md) "결과 파일"입니다. 시각은 모두 UTC입니다. 금액은 적지 않습니다(D74).

2회차 뒤 고친 것: 요청마다 나가는 query 줄이기(S147, PR #898). 인증 단계 한 query, 활성 시드 버전 30초 메모리, 문장 선택 기록 한 번에 읽기. 계정은 새로 만들었습니다(label 접두사 `r3`).

## 결론

* **요청 하나당 query가 5.9건에서 3.9건으로 34% 줄었습니다.** cold `stage_80` steady에서 초당 2,853건입니다.
* **cold 한계가 한 단계 올랐습니다.** 2회차 cold는 `stage_80`에서 멈췄고, 이번에는 `stage_80`을 p95 281ms로 버티고 `stage_160`에서 멈춥니다.
* **warm은 같은 단계에서 더 여유가 있지만 한계 단계는 그대로입니다.** `stage_80` p99가 2,983ms에서 405ms로 줄고, `stage_160`에서 멈추기 전 처리량이 758건/초에서 943건/초로 올랐습니다. #782 목표(초당 180세션, 약 1,650건/초)에는 아직 모자랍니다.
* **처음 막히는 곳은 여전히 Cloud SQL CPU입니다.** 두 회차 모두 `stage_80` 끝에 100%입니다.
* **SQL CPU의 대부분은 query 실행 밖에서 씁니다.** cold `stage_80` steady의 query 실행 시간 합은 1 vCPU의 약 24%이고, 유휴 CPU는 11%입니다. 나머지는 query와 트랜잭션마다 드는 통신, 암호화, 커밋 처리로 봅니다. query별 평균 실행 시간은 0.03~0.39ms이고 자주 부르는 query마다 맞는 인덱스가 있어, 실행 계획과 인덱스는 병목이 아닙니다.
