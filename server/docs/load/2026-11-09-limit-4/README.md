# L1 한계점 측정 4회차 (2026-11-09)

3회차는 [`../2026-11-09-limit-3/`](../2026-11-09-limit-3/README.md), 파일 형식은 [`load/README.md`](../../../load/README.md) "결과 파일"입니다. 시각은 모두 UTC입니다. 금액은 적지 않습니다(D74).

3회차 뒤 고친 것: 문장 선택 기록이 모두 있으면 트랜잭션과 advisory lock 없이 돌려줌(S148, PR #902). 계정은 새로 만들었습니다(label 접두사 `r4`).

## 결론

* **한계 단계는 3회차와 같습니다.** cold와 warm 모두 초당 80세션(요청 약 735건/초)을 버티고 `stage_160`에서 멈춥니다. warm `stage_160` warmup 처리량은 943건/초에서 989건/초로 조금 올랐습니다.
* **트랜잭션은 줄었습니다.** `stage_80` steady에서 BEGIN/COMMIT이 cold 401 → 233건/초(42% 감소), warm 389 → 208건/초(46% 감소)입니다. 문장 선택의 advisory lock과 트랜잭션 안 활성 시드 읽기도 상위 query에서 빠졌습니다.
* **SQL CPU는 거의 그대로입니다.** 같은 부하에서 cold 평균 90% → 86%, warm 85% → 87%입니다. warm은 statement가 13%(2,671 → 2,322건/초) 줄었는데도 CPU가 내려가지 않았습니다.
* **따라서 SQL CPU는 statement나 트랜잭션 수에 비례하지 않습니다.** 3회차에서 세운 "왕복 횟수가 CPU를 쓴다"는 가정은 이번 결과와 맞지 않습니다. query 실행 시간 합은 여전히 1 vCPU의 21~28%이고, 나머지를 무엇이 쓰는지는 이번 자료로 가르지 못했습니다. 왕복을 더 줄여 목표(약 1.75배)를 채울 근거는 없습니다.
