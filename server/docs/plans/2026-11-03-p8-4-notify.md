# P8-4 job notify Implementation Plan

> **agentic worker에게:** REQUIRED SUB-SKILL: 이 plan을 task 단위로 구현하려면 suberpower:subagent-driven-development(권장) 또는 suberpower:executing-plans를 사용하세요. Step은 추적을 위해 checkbox(`- [ ]`) 문법을 사용합니다.

**Goal:** 5분마다 도는 `server job notify`가 알림을 켠 사용자에게 현지 알림 시각 뒤 60분 안에 하루 한 번, 그날 총운 머리 문장(호칭 없음)을 FCM HTTP v1로 보냅니다.

**Architecture:** 새 표 `notification_log`(계정, 현지 날짜)가 하루 한 번을 지킵니다. 보내기 전에 행을 먼저 넣어(claim) 겹친 실행도 두 번 보내지 않습니다. 새 패키지 `internal/notify`는 대상 판정(Go 시각 계산, S128과 같은 이유), claim, 문장 만들기, 기기별 발송, 결과 기록을 맡습니다. FCM client는 `internal/notify/fcm.go`의 HTTP 호출과 재시도입니다. 문장은 `fortune.Views.Daily`(호칭 빈 값, 권한 `AlwaysLocked`)의 `daily.fortune.head`를 평문으로 편 것입니다. CLI `job notify`가 조립하고, Terraform이 Job과 5분 Scheduler를 만듭니다.

**Tech Stack:** Go, pgx/v5, sqlc, goose, `golang.org/x/oauth2/google`(ADC), `golang.org/x/sync/errgroup`, testcontainers, Terraform, GitHub Actions

**Spec:** `server/docs/specs/2026-10-11-server-mvp-design.md` §8.2, §3(`notification_log`), 결정 S13, D62, app 답 #603(메시지 형식)

**같은 PR에 묶음(D100 ①):** precompute가 대상이 있을 때만 엔진 버전을 조회하고 단계별 시간을 남기는 변경(commit `f550f3f6`, S128 보강)은 이 브랜치에 이미 있습니다.

## Global Constraints

* 대상: 계정 `active`, 프로필 `notify_status = 'enabled'`, 활성 기기 1대 이상, 현지 알림 시각이 [지금 − 60분, 지금] 안, 그 현지 날짜의 `notification_log` 행이 없음(spec §8.2).
* 알림 시각의 현지 날짜: 오늘 현지 날짜의 알림 시각이 지금보다 뒤면 어제 날짜의 알림 시각으로 봅니다(자정을 넘는 창, 예: 알림 23:50, 지금 00:20 → 어제 날짜).
* 하루 한 번: 보내기 전에 `notification_log`에 `(account_id, local_date)` 행을 `result = 'pending'`으로 넣고(이미 있으면 그 사용자는 건너뜀), 끝나면 `sent`·`failed`로 바꿉니다. claim 뒤 Job이 죽으면 그날은 보내지 않습니다(두 번 보내는 것보다 나음, S129).
* 메시지: 제목 없음, `body` = 그날 `daily.fortune.head` 문장(호칭 없음, 용어 토큰은 표시 글자만 이은 평문), `data = {"kind": "morning", "date": "YYYY-MM-DD"}`, Android `ttl` = 보낸 시각부터 다음 현지 자정까지 초(최소 1초), `notification.channel_id = "morning"`, `notification.tag = "morning"`, APNs `headers = {"apns-expiration": "<다음 현지 자정 unix 초>", "apns-collapse-id": "morning"}`.
* 기기별 발송, 동시 50개(spec §8.2). 한 사용자의 기기 중 하나라도 성공하면 `sent`.
* `UNREGISTERED`, 그리고 `INVALID_ARGUMENT` 중 잘못된 필드가 `message.token`인 응답은 그 기기를 비활성으로 바꿉니다(S92). 이 두 경우는 실패율에 넣지 않습니다(토큰 만료는 정상 흐름).
* `QUOTA_EXCEEDED`, `UNAVAILABLE`, `INTERNAL`(그리고 HTTP 429, 5xx)은 지수 backoff 1초, 2초, 4초로 3번까지 다시 보냅니다(spec §8.2).
* 실패율 = 실패한 메시지 수 / 보낸 메시지 수(문장을 만들지 못한 사용자는 메시지 1개 실패로 셈). 5%를 넘으면 Job 실패(spec §8.2). 대상 0명은 성공.
* 대상이 있을 때만 엔진 버전을 조회합니다(S128과 같은 이유).
* 로그에 계정 id, 토큰, 출생 정보, 문장을 남기지 않습니다. 수와 단계별 시간만 남깁니다.
* `notification_log`는 현지 날짜가 30일 지난 행을 `job retention`이 지웁니다(하루 한 번 판정에만 쓰므로, S129).
* Scheduler: `*/5 * * * *`, `Etc/UTC`. Job timeout(900s)이 간격보다 길어 실행이 겹칠 수 있으나 claim이 두 번 발송을 막습니다.

## Review Focus

1. 같은 사용자를 두 실행이 동시에 대상으로 골라도(겹친 실행) 메시지는 한 번만 갑니다.
2. 알림 시각 23:55, 현지 00:10에 처음 도는 실행은 어제 날짜로 보내고, `data.date`도 어제입니다. 같은 날 00:10 이후 알림 시각(예: 07:00)인 사람은 07:00 전에는 대상이 아닙니다.
3. DST로 없는 현지 시각(예: `America/New_York` 2027-03-14 02:30) 알림도 그날 한 번 갑니다. Go 정규화 시각(01:30 EST)부터 60분 창입니다.
4. 기기 3대 중 1대가 `UNREGISTERED`, 1대가 성공이면 결과는 `sent`, 그 기기만 비활성, 실패율에 들어가지 않습니다.
5. FCM이 계속 503이면 재시도 3번 뒤 실패로 세고, 대상 대부분이 그러면 Job이 실패합니다.
