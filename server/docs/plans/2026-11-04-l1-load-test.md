# L1 부하 테스트와 한계점 측정 Plan

> **agentic worker에게:** REQUIRED SUB-SKILL: 이 plan을 task 단위로 구현하려면 suberpower:subagent-driven-development(권장) 또는 suberpower:executing-plans를 사용하세요. Step은 추적을 위해 checkbox(`- [ ]`) 문법을 사용합니다.

**Goal:** 하루 사용 흐름을 요청 순서로 재현해 초당 요청을 단계적으로 올리고, 처음 막히는 곳(인스턴스 상한, DB 연결, 엔진)과 그때 server가 돌려주는 응답을 숫자로 남깁니다. 시나리오 S, M, L의 목표는 지휘가 #782에 남기면 같은 도구로 이어서 잽니다.

**Architecture:** 부하 생성은 k6 스크립트(`server/load/`)입니다. 대상은 같은 Terraform(`deploy/terraform/env`)으로 띄우고 끝나면 env만 지우는 부하 전용 GCP 프로젝트입니다. 요청은 실제 사용자와 같게 공개 주소(Firebase Hosting)로 보냅니다. 계정은 테스트 로그인(S24)으로 미리 만들어 두고, 측정은 k6 요청별 지표와 Cloud Monitoring 지표를 같은 시간 창으로 맞춰 읽습니다.

**Tech Stack:** k6 v2.3.0(`ramping-arrival-rate`, `--out csv`, `handleSummary`), Go(결과 집계 도구), Terraform, Cloud Run Job(부하 생성기), Cloud Monitoring API(`timeSeries.list`)

**Spec:** 준비 메모 `docs/specs/2026-10-30-capacity-observability-design.md` §4, 요청 #782, 결정 S24, S68, S133, S135, D74, D103, D104(환경 안 A, 결과 파일과 시각 리포트), 외부 준비물 E21, 지휘 코멘트(#782, 2026-11-04 결과 파일 요구)

## 정할 것과 추천

### 1. 도구: k6
* **고른 것:** k6. 도착률 고정(open model) 실행기가 있어, server가 느려져도 요청을 덜 보내지 않습니다. 실제 아침 몰림처럼 "느려지면 더 쌓이는" 상황을 재현합니다. 요청마다 tag를 붙여 종류별 지연과 상태 코드 분포가 나옵니다. threshold로 오류율이나 p95를 넘으면 단계를 멈출 수 있습니다.
* **버린 것:** vegeta는 요청 하나의 고정 비율만 보내, 로그인 뒤 여러 요청이 이어지는 흐름을 짜기 어렵습니다. Locust는 기본이 closed model이고, Python 실행 환경을 하나 더 둬야 합니다.
* **위치:** `server/load/`
  * `lib/`: 계약 형식 요청 함수, 계정 풀 읽기
  * `scenarios/`: `smoke.js`, `ramp.js`, 나중에 `target.js`
  * `accounts/`: 계정 만들기 스크립트(결과 토큰은 저장소에 넣지 않고 `.local/`)
  * `README.md`
* **버전 고정:** 로컬은 `grafana/k6:2.3.0` 컨테이너, 생성기 Job도 같은 이미지입니다.

### 2. 환경: 부하 전용 프로젝트 (D104로 결정)
안 A로 정해졌습니다(사용자 결정, D104 ①). 아래 표는 고른 근거로 남깁니다. 사용자 준비는 외부 준비물 E21이고, server가 `load.tfvars`와 절차(L1-3)를 올리면 사용자가 진행합니다.
| 안 | 좋은 점 | 비용과 준비 |
| --- | --- | --- |
| **A. 부하 전용 프로젝트 `myungli-diary-load`** (결정) | staging을 흔들지 않음. prod와 같은 SQL tier로 띄워 한계가 prod를 대표함. env만 destroy하고 다시 apply하면 회차마다 새 상태 | 사용자 한 번: 프로젝트 생성과 결제 연결, Firebase 추가, bootstrap apply, Secret 값 복사. 자원 비용은 env가 떠 있는 동안만(회차당 몇 시간) |
| B. staging에서 짧게 | 준비가 거의 없음 | `db-f1-micro`(연결 25)라 prod와 다른 곳에서 막힘. T1이 시작되면 테스터 시간을 피해야 하고, 테스트 계정과 데이터가 staging DB에 쌓임 |
| C. staging 프로젝트 안에 env 하나 더 | 프로젝트를 새로 만들지 않음 | 모든 자원 이름에 접미사 변수를 넣는 리팩터링, Hosting site와 DNS zone 분리가 필요해 A보다 일이 큼 |

* A의 env는 `load.tfvars`로 띄웁니다. 회차가 끝나면 비용이 큰 Cloud SQL만 지웁니다(L1-3 Step 2).
  * SQL tier와 `sql_max_connections`는 prod와 같게 합니다.
  * Scheduler(precompute, notify, retention)는 멈춥니다. 측정 중 배치가 끼지 않게 하고, precompute는 측정 전에 손으로 한 번 돌립니다.
  * uptime check는 끄고, 알림 channel은 둡니다. 한계에 닿을 때 O1 알림이 실제로 오는지도 함께 봅니다.
  * 외부 로그인 값(Kakao, LINE, Apple)은 staging의 공개 값을 그대로 씁니다. 테스트 로그인만 쓰므로 실제로 불리지 않습니다.
* bootstrap은 새 프로젝트에 처음 apply하는 것이라 기존 두 프로젝트의 D103 묶음과 상관없습니다. bootstrap 코드를 바꿔야 하면(예: 예산 알림을 끄는 변수) 그 변경은 D103 묶음 목록에 넣습니다.
* 공개 문서에는 금액을 적지 않습니다(D74). 결과에는 자원 사용량(인스턴스 초, vCPU 초, SQL CPU)만 적고, 금액 계산은 지휘에게 넘깁니다.

### 3. 사용 모델 (요청 순서)
app 코드를 읽어 확정했습니다(2026-11-04, 읽기만, 근거 파일은 `server/load/lib/flows.js` 머리 주석). 세션 하나는 "사용자 한 명이 앱을 한 번 여는 것"이고 도착률 단위는 세션/초입니다.

| 흐름 | 요청 순서 | 세션당 확률(기본) |
| --- | --- | --- |
| 앱 열기(아침 알림을 눌러 열어도 같음) | `getAppConfig` → `refreshToken`(access token은 메모리에만 있어 열 때마다) → `getMe` | 늘 |
| today 화면 | `getDaily`(오늘), `getGlossary`(If-None-Match, 대부분 304), `listDiaries`(오늘), `listSchedules`(오늘)를 동시에 | 늘 |
| 반응 | `putReaction`(그날 총운 머리 문장) | 10% |
| 일기 쓰기 | `getDaily`(그날) → `createDiary`(Idempotency-Key) → `getDiary`(id) → `listDiaries`(오늘) | 25% |
| 캘린더 | `getCalendar` 석 달(앞, 이번, 다음), `listSchedules`와 `listDiaries`(42칸 격자), `getGlossary`를 동시에 | 20% |

* app은 진입 때 `getEntitlements`, `getChart`를 부르지 않습니다. 알림 기기 등록(`registerDevice`)은 FCM 토큰이 바뀔 때만이라 넣지 않았습니다.
* app은 429, 503, 시간 초과에 자동 재시도하지 않고 사용자가 "다시 시도"를 누를 때만 다시 보냅니다(`app/lib/core/api/http_client.dart:62-92`, provider `retry: null`). 그래서 재시도 폭주는 server 쪽 걱정거리가 아니고, 스크립트도 다시 보내지 않습니다. 시간 제한은 connect 10초, send와 receive 20초입니다.
* smoke(2026-11-04, 초당 2세션 2분)에서 세션 하나는 요청 9~10개였습니다.

* **최고점:** 같은 알림 시각을 고른 사용자 비율과, 알림 뒤 몇 분 안에 여는지는 시나리오 변수로 둡니다. 지휘의 S, M, L 목표가 오기 전에는 도착률만 올립니다.
* **엔진 캐시:** 회차마다 두 갈래로 잽니다. precompute를 먼저 돌린 적중(warm)과, 돌리지 않은 미적중(cold, 첫 `getDaily`가 엔진을 부름)입니다.
* **계정:** 테스트 로그인으로 계정을 만들고(`accounts.js`), 동의와 프로필 생성까지 해 둡니다. 출생 정보는 고루 나눠 엔진 캐시가 한 사주로 몰리지 않게 합니다. 측정 setup이 계정을 모두 로그인해 갱신 토큰을 받고, VU 하나가 계정 하나를 맡아 갱신 토큰(한 번 쓰면 바뀜)을 두 VU가 함께 쓰지 않게 합니다. 계정 수는 VU 수 합 이상이어야 합니다.
* **cold와 warm:** cold는 `DAILY_OFFSET_DAYS`로 today 화면의 날짜를 아직 계산하지 않은 날로 옮깁니다(`getDaily`는 날짜 제한이 없음). warm은 precompute 뒤 오늘입니다.

### 4. 측정과 한계 확인
* **단계:** 단계마다 도착률을 고정한 scenario(`constant-arrival-rate`, 이름 `stage_<세션/초>`)를 하나씩 두고 차례로 돌립니다. 처음 계획한 `ramping-arrival-rate`의 올리는 구간을 없애, 단계 경계가 scenario tag로 바로 나오고 멈춤 조건도 단계마다 따로 겁니다.
  * 기본은 초당 2 → 5 → 10 → 20 → 40 → 80 → 160 → 320세션(요청으로 약 19 → 3,000건/초)입니다. 단계마다 3분, 사이 30초 쉼입니다. 상한은 #782 목표 최고점(L 180, L-1월 270)보다 높게 두어, 멈춤 조건에 닿을 때까지 갑니다.
  * 계정은 모든 단계 VU의 합(기본 3,185)만큼 둡니다(`ACCOUNTS=3200`). VU가 단계마다 따로이고 갱신 토큰을 VU끼리 넘길 수 없기 때문입니다.
  * 단계마다 오류율(4xx, 5xx, 시간 초과)이 1%를 넘거나 `getDaily` p95가 2초를 넘으면 k6가 그 단계에서 멈춥니다(threshold `abortOnFail`).
  * 판정은 단계 처음 30초(`STAGE_WARMUP`, tag `phase=warmup`)를 빼고 그 뒤(`phase=steady`)에만 겁니다. 2026-11-05 cold 1회차가 `stage_40` 시작 7초의 증설 구간 표본(getDaily p95 2,082ms)으로 멈췄기 때문입니다. warmup 구간은 `stages.csv`에 따로 남겨 증설 중 지연도 결과로 봅니다.
  * 멈춘 단계의 바로 아래가 그 설정의 한계점입니다.
* **k6에서 받는 것:** 요청 종류별 p50, p95, p99, 상태 코드 분포, 시간 초과 수, 실제 도착률. 회차 전체 요약과 단계별 집계를 결과 파일로 남깁니다(§5).
* **Cloud Monitoring에서 받는 것(같은 시간 창):**
  * server와 엔진의 인스턴스 수, 요청 지연, 컨테이너 CPU와 메모리
  * Cloud SQL CPU, `num_backends`, 디스크 I/O
  * 엔진 요청 수(적중률은 server의 엔진 호출 수 ÷ `getDaily` 수로 계산)
* **한계에서 기록할 것:**
  * 어디가 먼저 막혔는지
  * 그때 응답: Cloud Run 상한의 429, DB 풀 대기 끝의 5xx, Hosting이나 server의 시간 초과
  * O1 알림 도착 여부
  * 단계가 끝나고 몇 분 만에 정상으로 돌아오는지
* **app 대응:** 한계에서 나온 응답 종류(429, 503, 시간 초과)를 적어 `to:app` Issue로 재시도 폭주와 안내를 확인해 달라고 올립니다. server는 app 코드를 고치지 않습니다.

### 5. 회차 결과 파일 (D104 ②, 지휘 요구)
지휘가 회차마다 비공개 시각 리포트를 만들 수 있게, 사람이 읽는 표와 함께 기계가 읽는 파일을 저장소에 남깁니다. 위치는 `server/docs/load/<날짜>-<회차>/`이고 열 이름과 단위는 `server/load/README.md`에 적습니다. 금액은 어느 파일에도 넣지 않습니다(D74).

| 파일 | 내용 | 만드는 곳 |
| --- | --- | --- |
| `README.md` | 사람이 읽는 표: 회차 설정(warm/cold, 계정 수, 이미지 digest), 단계별 요약, 처음 막힌 곳, 한계 응답, 자원 사용량 합계 | 손으로, 아래 파일을 보고 |
| `k6-summary.json` | k6 `handleSummary`의 회차 전체 요약. 갱신 토큰이 든 `setup_data`는 뺌 | k6 |
| `stages.csv` | 단계마다 `all`과 operation별 한 줄. phase(`all`, `warmup`, `steady`)마다 나눔. 열: `stage_rate`(세션/초), `stage_start_utc`, `stage_end_utc`, `phase`, `operation`, `requests`, `actual_rps`, `p50_ms`, `p95_ms`, `p99_ms`, `status_2xx`, `status_304`, `status_429`, `status_5xx`, `status_other`, `timeouts`, `blocked`(그 단계에서 멈춤 조건에 닿았는지) | 집계 도구가 k6 `--out csv` 원자료에서 |
| `monitoring.csv` | 같은 시간 창의 1분 간격 시계열. 열: `time_utc`, `metric`, `resource`(server, engine, sql), `value`, `unit`. 대상: server와 엔진의 인스턴스 수, 요청 수, 요청 지연 p95, 컨테이너 CPU 사용률, Cloud SQL `num_backends`와 CPU 사용률 | 집계 도구가 Monitoring API에서 |
| `usage.csv` | 자원 사용량 합계. 열: `resource`, `instance_seconds`, `vcpu_seconds`, `memory_gib_seconds`, `sql_hours` | 집계 도구가 `monitoring.csv`와 서비스 설정(CPU 1, 메모리 0.5GiB)에서 |

* **단계 구분:** k6 원자료(`--out csv`)의 `scenario` 열(`stage_<세션/초>`)로 나눕니다. setup 요청은 scenario가 없어 빠집니다. operation은 `extra_tags` 열에 있습니다.
* **집계 도구:** `server/load/report/`(Go, `go run`)가 원자료 CSV와 단계 설정으로 `stages.csv`를 만듭니다. Monitoring API `projects.timeSeries.list`(ADC)로 `monitoring.csv`와 `usage.csv`를 만듭니다. 원자료 CSV는 크므로 저장소에 넣지 않고 `.local/load/`에 둡니다.
* **지표 이름:** Cloud Run `run.googleapis.com/container/instance_count`, `request_count`, `request_latencies`, `container/cpu/utilizations`, `container/billable_instance_time`과 Cloud SQL `cloudsql.googleapis.com/database/postgresql/num_backends`, `database/cpu/utilization`을 씁니다. 2026-11-04 부하 프로젝트에서 metricDescriptors와 timeSeries.list로 이름, 종류, 응답 모양을 확인해 README에 굳혔습니다.
