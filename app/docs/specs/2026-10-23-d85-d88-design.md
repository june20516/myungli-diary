# 계정 삭제·구매 내역 따라잡기 (D85·D88) 설계

* 작성: app 세션, 2026-10-23
* 상태: 승인(2026-10-23), 구현 브랜치 `app/d85-d88`
* 요청: Issue #504 (drift), #518 (REST draft.15), #484 (D85 연결 거절·합치기 별도 흐름·삭제 복구 없음), #493 (D88 구매 내역)
* 관련 결정: 루트 D85·D88·D89·D90, server S105~S114, design V44~V46, writing W39·W40·W42
* 쓰는 계약: REST `server/api/openapi.yaml` `1.0.0`(freeze, S114. `deleteMe`·`getMe`·`listPurchases`·`restorePurchases`·`previewMerge`·`mergeAccounts`), IA `ad-free`·`purchase-history`·`account-delete`·`login-methods`·`account-merge`, design 컴포넌트 3.0.0(`offer-card`·`purchase-row`·`account-choice`·`social-login-button`·`diary-row`·`dialog`), writing ARB(W40)
* 바탕 문서: 계획 7 spec·계획(`app/real-login` 브랜치의 `docs/specs/2026-10-21-real-login-design.md`, `docs/plans/2026-10-22-real-login.md`). 이 브랜치로 가져와 §7대로 고칩니다

## 1. 목적과 범위

drift #504와 draft.15(#518), 그 뒤 freeze된 REST 1.0.0(S114)과 D90 IA를 맞추고, 그 계약으로 지금 있는 계정 삭제 흐름을 D85 ⑤로 바꾸고, 구매 내역 화면과 그 입구인 광고 제거 화면을 만듭니다(#493). 로그인 수단·계정 합치기 화면은 계획 7에서 만들고, 이 브랜치는 그 계획 문서를 D85·draft.15에 맞게 고칩니다(#484).

**성공 기준**
* ci-gate의 app drift 검사와 app 전체 검사(analyze, 전체 테스트, golden, 커버리지 ratchet)가 통과합니다.
* 계정을 지우면 204 뒤 바로 로그아웃되어 `welcome`으로 갑니다. 삭제 대기 상태를 다루는 코드가 남지 않습니다.
* 설정 → 광고 제거 → 구매 내역으로 들어가면, 사용자에게 알리지 않고 결제 기록을 다시 맞춘 뒤 이 계정의 구매가 줄로 보입니다.
* `ia_pending.dart`에서 `ad-free`·`purchase-history`가 빠집니다.
* 동의는 했지만 사주가 없는 계정이 미리보기 입력을 가진 채 로그인하면 `onboard-call`을 거치지 않고 저장 뒤 `notify-ask`로 갑니다(D90 ③).

**다루지 않는 것**
* 실제 RevenueCat SDK adapter와 iOS sandbox에서 `syncPurchases`가 Apple ID 로그인 창을 띄우는지 확인(계획 7, 외부 준비물 필요). #493에 알립니다.
* LINE·Google SDK 허가 취소(adapter가 계획 7에서 생김). 계정 삭제 전 취소 자리는 계획 7 문서에 적습니다.
* `login-methods`·`account-merge` 화면과 연결·합치기 데이터 경계(계획 7 단계 B).
* D89 설정 "문의하기" 줄. IA 슬롯과 문의 주소가 아직 없습니다.
* D90 ① 일기 보기의 그날 성격(기록한 값). server가 `Diary`에 선택 필드를 더하는 계약 minor가 아직 없습니다. 들어오면 따로 맞춥니다.
* D90 ② 미리보기 총운의 호칭. app은 server 문장을 그대로 보이므로 바꿀 것이 없습니다(IA 설명만 바뀜).

## 2. 계약 따라잡기

* **생성물:** `gen_ia`·`gen_tokens`·`import_writing_arb`·`gen-l10n`·`gen_api.sh`를 다시 돌립니다. draft.15에서 `DeletionScheduled`·`IdentityInUseProblem`·`MergeResult` 등이 없어지고 `Purchase`·`MergeSummary`·`MergeProfile` 등이 생깁니다.
* **열린 enum:** `PurchaseStatus`를 `mark_open_enums`·`open_enums_contract_test`에 올립니다. 모르는 값은 그 값 그대로 읽고, 화면은 기본 표시(§5)로 보입니다.
* **REST 1.0.0 열린 enum(S114, 결정 A78):** `YongsinMethod`·`SlotText.reaction`·`Language`가 열린 enum이 됩니다. `Language`의 모르는 값은 기본 언어(`Language.en`, 기기 언어 판정의 기본값과 같음)로 보고 씁니다(호칭 길이 상한, 설정 언어 이름). `SlotText.reaction`의 모르는 값은 반응 없음으로 그립니다. `YongsinMethod`는 app이 읽지 않아 decode만 견딥니다.
* **같은 날 일기(1.0.0 `listDiaries`):** 합친 계정은 한 날짜에 10편을 넘을 수 있어 `diariesOn`도 `nextCursor`를 끝까지 따라갑니다(`datesIn`과 같은 상한). A69의 "한 쪽으로 끝남"을 바꿉니다.
* **ARB:** writing에 없는 app 전용 키 가운데 IA에서 빠진 슬롯의 키(`adFreeRestoreCta` 등)를 지웁니다.

## 3. 계정 삭제 (D85 ⑤, 결정 A73)

* `deleteMe`는 204이고 본문이 없습니다. 성공하면 server가 세션을 모두 지운 뒤이므로 server `logout`을 부르지 않고 로컬 로그아웃(`TokenStore.signOut`)만 합니다. 이후 정리는 지금처럼 `signedOut` 이벤트가 맡습니다.
* 실패하면 지금처럼 로그인 상태 그대로 오류 toast와 다시 시도입니다. 401이면 이미 지워진 것과 같으므로 로컬 로그아웃합니다.
* 진입 계산의 삭제 대기 갈래(`isPendingDeletion`과 `entry_providers`의 `revokeAndSignOut` 호출)를 지웁니다. `Me.status`·`deletionScheduledAt`·`LoginResponse.restoredFromDeletion`이 없어졌기 때문입니다. `revokeAndSignOut`은 설정의 로그아웃(`settings_controller`)이 계속 씁니다.
* 화면 문구는 W40 원고(`accountDeleteDataBody`: 바로 지워지고 되돌릴 수 없음)를 그대로 씁니다.

## 4. 화면이 문구를 맡는 problem code (결정 A74)

* `auth.identity_pending_deletion`은 계약에서 없어졌으므로 `problemMessages`에서 지웁니다.
* `merge.token_invalid`은 W42로 `errorMergeTokenInvalid`가 생겼으므로 `problemMessages`에 넣습니다(다른 code와 같은 규칙).
* `merge.same_account`·`merge.no_account`은 `error…` 키가 없습니다. writing이 `account-merge` 화면 문구 `account-merge.not-other.body`(`accountMergeNotOtherBodySelf`·`accountMergeNotOtherBodyNone`)로 정했습니다(W42).
* `problem_codes_contract_test`에 `_screenMessages`(code → 화면이 쓰는 ARB 키)를 두고, 그 키가 세 언어 ARB에 있는지 대조합니다. 이 두 code는 `problemMessages`에 넣지 않고(일반 경로로 오면 4xx 일반 문구), 화면 연결은 계획 7 `account-merge`가 합니다. `_awaitingWriting`은 빈 집합이 됩니다.

## 5. 구매 데이터 (결정 A75·A76·A77)

**`Purchases`(플랫폼 인터페이스) 변경**
* `restore()`를 지우고 `Future<void> sync()`를 둡니다. RevenueCat `syncPurchases`에 해당하며 사용자에게 아무것도 띄우지 않는 것이 전제입니다(iOS 확인은 계획 7). 실패하면 `AppError`를 던집니다.
* `StoreProduct`에 `title`(스토어가 현지화한 상품 이름)을 더합니다. fake 카탈로그도 채웁니다.

**상품 이름(A77)**
* 광고 제거권 상품 id는 저장소에 두지 않으므로(S89, D74) 빌드 설정 `--dart-define=AD_FREE_PRODUCT_IDS`(쉼표 목록)로 받습니다. fake 모드 기본값은 fake 카탈로그의 id입니다.
* 이름은 차례대로: 상품 id가 광고 제거권 목록에 있으면 `purchaseProductAdFreeMonth` → `Purchases.products()`에서 같은 id의 `title` → 상품 id 그대로. 순수 함수로 두고 단위 테스트합니다.

**`PurchaseRepository`(`features/purchase/data`)**
* `list()` → `listPurchases`의 `items`를 server 순서 그대로 돌려줍니다.
* `reconcile()` → `restorePurchases`.

**구매 내역 불러오기(A76)**: 화면에 들어갈 때마다 한 번 순서대로 부릅니다.
1. `Purchases.sync()`
2. `PurchaseRepository.reconcile()`. 성공하면 `meProvider`를 새로 받습니다(남은 기간이 바뀔 수 있음).
3. `PurchaseRepository.list()`

* 1·2가 실패해도 사용자에게 알리지 않고 다음 단계로 갑니다. 예상 밖 오류는 요약만 crash 기록에 남깁니다(D64). 오프라인이면 1·2를 건너뛰지 않고 그대로 시도하며, 화면 상태는 3의 결과로 정합니다.
* 3이 `OfflineError`면 `offline`, 그 밖의 실패면 `error`(다시 시도는 1부터), 빈 목록이면 `empty`입니다.

**상태 낱말:** `active` 사용 중(`tag.status`), `pending` 사용 전, `expired` 만료, `refunded` 환불. `owned`와 모르는 값은 writing 낱말이 없어 상태 자리를 비웁니다.

## 6. 화면

**`offer-card` 컴포넌트**(`lib/design/components/…`, design `action.md` 3.0.0 명세 값 그대로): 아이콘 → `offer.head` → 가격(`adFreeOfferPrice`, `{price}`) → 구매 주 버튼 → 구매 내역 조용한 버튼(`ad-free.history.cta`, 상태와 관계없이 늘 보임) → 약관 안내. `offline`은 구매 버튼만 비활성입니다. 구매 중에는 구매 버튼 `loading`. contract 대조, golden, widgetbook을 둡니다.

**`ad-free` 화면(A75)**
* 상품은 `Purchases.products()`의 광고 제거권 상품(목록의 첫 상품)입니다. 받는 동안 `loading`, 실패면 `error`, 오프라인이면 `offline`.
* 남은 기간은 `Me.adFree`(활성이면 `adFreeStatusRemaining`). `AdFree.expiresAt`은 이어 붙인 대기 구간까지 포함한 끝이므로(REST 1.0.0) 그 날짜를 그대로 "까지"로 보입니다.
* 구매: 구매 버튼 → `Purchases.buy`(IA `system-purchase`는 OS 결제 시트이며 app 화면이 아님). 성공하면 햅틱 light, `restorePurchases`로 장부를 맞추고 `meProvider`를 새로 받습니다(웹훅 지연을 기다리지 않음). `restorePurchases`가 실패해도 구매 성공으로 보고 `Me`만 새로 받습니다. 취소면 아무 일 없음, 실패면 오류 toast.
* 출구: 약관 링크 → `legal`, 구매 내역 버튼 → `purchase-history`.
* 구매 버튼 문구: IA `ad-free`에 구매 버튼 슬롯이 없고 writing 키도 없습니다. 지휘에 IA 슬롯 `ad-free.buy.cta`와 원고를 Issue로 요청하고, 받기 전에는 A7대로 app 임시 키 `adFreeBuyCta`("구매하기")를 씁니다.
* 사용 중 꼬리표(`offer-card` `status`)는 `purchaseStatusActive`, 그 아래 남은 기간 글자(`remaining`)는 `adFreeStatusRemaining`입니다.

**`purchase-row` 컴포넌트:** 묶음 카드 하나에 줄들(줄 사이 1px `line`), 부품 `product`·`status`·`meta`, 누르지 않음, 스크린리더는 한 줄을 "상품 이름, 상태, 구매일, 사용 기간" 한 덩어리로 읽습니다. `meta`는 구매일(`purchaseMetaPurchased`, 기기 locale 짧은 날짜) + 구분자 + 사용 기간(`purchaseMetaPeriod`, 기간 없으면 구매일만). 날짜는 기기 시간대 기준입니다. skeleton 줄 세 개. contract 대조, golden, widgetbook을 둡니다.

**`purchase-history` 화면:** app-bar → 위 `space.12` 묶음 카드 → `missing.notice`(목록이 있든 `empty`든 보임, `loading`·`error`·`offline`에서는 없음). `empty`는 `empty-state`(아이콘 `receipt`, `purchase-history.empty.body`, 버튼 없음) 아래 `space.16`에 `missing.notice`.

## 6a. 동의·사주 없는 기존 계정의 로그인 갈래 (D90 ③, 결정 A79)

* 로그인 뒤 진입 계산 결과가 `profileRequired`(동의는 함, 사주 없음)이고 이 기기에 다 받은 온보딩 입력(미리보기 입력)이 있으면, 로그인 화면이 `OnboardingCompleter.complete()`로 저장한 뒤 `notify-ask`로 갑니다. 동의 화면의 같은 처리(`consent_controller`)와 같은 규칙입니다: 입력 오류(422)면 `OnboardingRejectionNotice`를 남기고 `onboard-call`, 그 밖의 실패는 진입만 다시 계산해 `onboard-call`이 다시 저장합니다.
* 입력이 없으면 지금처럼 `onboard-call`, 동의가 없으면 `consent`입니다.
* `login` 출구에 `notify-ask`·`onboard-call`, `launch` 출구에 `consent`·`onboard-call`을 IA대로 더합니다(라우터 갈래는 이미 있음).

## 7. 계획 7 문서 개정 (#484)

`app/real-login`의 spec·계획을 이 브랜치로 가져와 고칩니다. 바뀌는 것:
* **결정 번호:** 두 문서가 쓰던 A67~A72는 일기 결정과 겹치므로 A80부터 다시 매깁니다.
* **연결(D85 ③):** `linkIdentity` 409 `auth.identity_in_use`·`auth.provider_taken`이면 `login-methods.in-use.body`를 `dialog` `notice`로 보이고 이 화면에 남습니다. 합치기로 넘어가지 않습니다. `auth.identity_pending_deletion`은 없어졌습니다.
* **합치기 입구:** `login-methods` 아래 가로선과 `primary-button` `quiet` `login-methods.merge.cta`(늘 보임).
* **`account-merge` 두 단계(V44):** 인증 단계(네 버튼, `login`과 같음) → 제공자 증명으로 `previewMerge`(`MergePreviewRequest`) → 422 `merge.same_account`·`merge.no_account`면 `not-other` dialog 뒤 인증 단계에 남음, 요약 실패면 `accountMergeError` dialog 뒤 인증 단계 → 요약·고르기 단계(요약 상자: 일기 편수·일정 개수(1.0.0에서 살아 있는 기록만 셈, 지운 기록도 옮기지만 세지 않음)·광고 제거 남은 기간(있을 때만), `account-choice` A·B로 프로필 고르기, 고르기 전 합치기 버튼 비활성) → 최종 확인 → `mergeAccounts`(`{mergeToken, profile}` + `Idempotency-Key`, 응답 `Me`, 토큰 교체 없음). "합치지 않기" 버튼은 없고 뒤로 가기가 그만두기입니다. 합치는 동안 뒤로 가기를 모두 막습니다. 409 `idempotency.in_progress`면 잠시 뒤 같은 키로 다시 보내고, 같은 키 재전송이 422 `merge.token_invalid`면 `getMe`로 합쳐졌는지 확인합니다. 합쳐지지 않았으면 `errorMergeTokenInvalid`(W42)를 보이고 인증 단계로 돌아갑니다.
* **SDK 허가 취소:** 합치기에서 B의 증명에 LINE·Google을 썼으면 합친 뒤 그 SDK 허가를 취소합니다. 계정 삭제 전에도 이 기기에 LINE·Google 제공자 token이 있으면 취소합니다(카카오·Apple은 server).
* **이미 끝난 일:** `account-choice`(3.0.0 반영 포함)·`social-login-button` 컴포넌트, draft.15 생성 클라이언트, 계정 삭제 204 처리. 해당 Task는 끝남으로 표시하고 남은 일만 둡니다.
* **RevenueCat adapter 과제:** `Purchases.sync()`의 실제 구현과 iOS sandbox 확인(Apple ID 로그인 창을 띄우면 지휘에 알림)을 계획 7 수익 쪽 과제로 적습니다.

## 8. design 3.0.0 값 (V46 등)

* `social-login-button`: 카카오 `connected` 배지 심볼 `#191919`, LINE 글자 자리 198px(다른 제공자 232px).
* `diary-row` `entry`: 시각 24시간제 `HH:mm`(앞 0 채움, locale 형식 아님), 꺾쇠 앞 `space.8`.
* `account-choice`: 부품 `facts`·`diaryCount`·`providers` 삭제, 알약 `current`(A 카드)·`other`(B 카드, `accountChoiceOther`), 카드 순서 A → B.
* `dialog` `notice`: 쓰임만 늘어남(값 변화 없음).
* contract 값 대조를 3.0.0으로 올리고 바뀐 golden을 다시 만듭니다.

## 10. 오류와 경계
